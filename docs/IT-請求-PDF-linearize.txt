========================================
SCCD 網站 — 請 IT linearize 既有圖書館 PDF（Fast Web View）
最後更新：2026-08-12
========================================

問題：
  圖書館「文件」點進去看，大本掃描 PDF 開啟要 10 秒以上。
  原因＝這些 PDF 沒有「線性化（Linearized / Fast Web View）」。
  非線性化的 PDF，物件索引在檔案「尾端」，瀏覽器(pdf.js)必須先抓檔尾、
  再一趟趟 HTTP Range 追物件才拼得出第一頁 → 上百頁的大本就拖到十幾秒。

  這是 web 開 PDF 的業界標準前處理（等同 Adobe Acrobat「另存 → 最佳化 →
  快速 Web 檢視」）。線性化把「第一頁＋索引」搬到檔案最前面，一兩趟 Range 就
  能顯示第一頁 → 開啟從 >10s 降到約 1 秒。前端與伺服器都已支援 Range，
  只差把既有檔案 linearize 這一步。

  ★ 無損、不改內容、不改檔名/UUID、檔案大小幾乎不變，只是把內部結構重排。


重要前提（跟原本估計不同）：
  這站的 Directus 檔案存放在 **S3**（不是伺服器本機硬碟）。所以不能「就地改
  uploads 資料夾」，要對 S3 物件做：下載 → linearize → 傳回同一個 key。
  檔案在 S3 的 key ＝ Directus 的 filename_disk ＝ <UUID>.pdf（可能有共同前綴，
  見下方從 .env 讀 STORAGE_S3_ROOT）。

影響範圍：
  圖書館文件共 121 個 PDF、最大單檔 126 MB。
  完整檔名清單（121 行，每行一個 <UUID>.pdf）＝隨附 docs/linearize-pdf-list.txt。
  ※ 走 S3 直傳、不經過網站的上傳通道，所以「上傳大小上限」在這裡完全不相干
     （那個 126MB 的檔也能照做）。


請 IT 做：

0. 準備：安裝工具（伺服器上多半已有 aws cli；qpdf 通常要裝）
     sudo apt-get update && sudo apt-get install -y qpdf awscli

1. 從 Directus .env 讀出 S3 設定（bucket / region / 前綴 / 金鑰）：
     grep -i "STORAGE" /home/bitnami/directus-cms/.env
   會看到類似（變數名以實際 .env 為準）：
     STORAGE_S3_BUCKET=xxxx
     STORAGE_S3_REGION=ap-northeast-1
     STORAGE_S3_ROOT=            # 可能空白，或是一段 key 前綴，如 "uploads/"
     STORAGE_S3_KEY / STORAGE_S3_SECRET  （或這台 EC2/Lightsail 掛了 IAM role，就不用金鑰）
   把 bucket 與 root 記下來：
     BUCKET=<STORAGE_S3_BUCKET 的值>
     ROOT=<STORAGE_S3_ROOT 的值，沒有就留空>

2. 把隨附的 linearize-pdf-list.txt 上傳到伺服器（例如放 ~/linearize-pdf-list.txt）。

3. ★★ 先只測「一本」，確認整條路走得通再批次 ★★
     f=$(head -1 ~/linearize-pdf-list.txt)
     aws s3 cp "s3://$BUCKET/${ROOT}$f" /tmp/in.pdf
     qpdf --linearize /tmp/in.pdf /tmp/out.pdf
     aws s3 cp /tmp/out.pdf "s3://$BUCKET/${ROOT}$f" --content-type application/pdf
   然後到網站圖書館打開這一本，確認：
     (a) 開得起來、頁數正確、內容正常
     (b) 開啟明顯變快
   → 沒問題再繼續第 4 步；有問題先停下來回報（S3 物件已被覆蓋，但可從你自己的
     備份或原檔還原；建議測試前先 aws s3 cp 把這一本另存一份當備份）。

4. 批次處理其餘 120 本（已 linearize 的自動略過、失敗的保留原檔不動）：

     while read f; do
       [ -n "$f" ] || continue
       aws s3 cp "s3://$BUCKET/${ROOT}$f" /tmp/in.pdf --quiet || { echo "MISS $f"; continue; }
       if qpdf --check /tmp/in.pdf 2>/dev/null | grep -qi "linearized: yes"; then
         echo "SKIP $f (已 linearized)"; continue
       fi
       if qpdf --linearize /tmp/in.pdf /tmp/out.pdf 2>/dev/null; then
         aws s3 cp /tmp/out.pdf "s3://$BUCKET/${ROOT}$f" --content-type application/pdf --quiet \
           && echo "OK   $f"
       else
         echo "SKIP $f (qpdf 無法處理，原檔不動)"
       fi
     done < ~/linearize-pdf-list.txt


需要 IT 留意的兩個點（就是為什麼第 3 步要先測一本）：
  - Content-Type：aws s3 cp 覆蓋時務必帶 --content-type application/pdf，
    否則 S3 物件可能變成 application/octet-stream，瀏覽器/播放器會出錯。
  - 瀏覽器快取：檔案設了 30 天 Cache-Control。既有訪客的瀏覽器可能仍拿到舊檔，
    直到快取過期或 ETag 改變才更新。第一次看的訪客與無痕視窗不受影響。
    若要讓所有人立刻拿到新檔，可在後台把該檔 modified_on 動一下（touch），
    或由我們前端加版本參數——這點測完再決定要不要處理。


之後「新上傳的 PDF」怎麼辦：
  由上傳的人在 Acrobat 存檔時勾「快速 Web 檢視（Fast Web View）」再上傳，
  檔案本身就已 linearized，不需要 IT 再處理、也跟存 S3 無關。
  （所以這份請求是「一次性把既有 121 本補做」，不是長期任務。）
